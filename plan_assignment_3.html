Overview

Design a 1D linear Kalman filter that estimates the distance to the wall in front, test it offline on logged data, then run it on the robot inside the given control loop that keeps the robot at a fixed distance from the wall.

$$\bar{\mathbf x} = \mathbf F\mathbf x + \mathbf B\mathbf u,\quad \bar{\mathbf P} = \mathbf F\mathbf P\mathbf F^\mathsf T + \mathbf Q \qquad \mathbf y = \mathbf z - \mathbf H\bar{\mathbf x},\quad \mathbf K = \bar{\mathbf P}\mathbf H^\mathsf T(\mathbf H\bar{\mathbf P}\mathbf H^\mathsf T + \mathbf R)^{-1}$$

The three parts of the assignment:

  1. Design the filter: process model F, B, its uncertainty Q, and measurement model H, R. For three cases:
    • Mandatory Simple case: state = distance to the wall only, inputs = wheel speeds \((\omega_A, \omega_B)\). → Steps 0–9
    • To impress Extended case: add the IMU measurements to that model. → Step 10
    • To really impress Extended case v2: state = distance + wheel speeds, inputs = motor voltages (motor model). → Step 11
  2. Simulate the filter in Python on data (inputs + measurements) logged on the robot.
  3. Run the filter on the robot by editing robot.cpp and state_estimator.cpp. Don't change the velocity controller or the control algorithm; only the gain K of the position controller.

Template update 16 Oct: the state is now the distance in metres (not wheel radians), the feedback is K * (_xhat - xref), and the QRC channels were renumbered. This plan follows the new template. Summary of every change and trap: experiences/TEMPLATE_CHANGES_AND_PITFALLS.MD.

Deliverable: the Arduino script + the relevant Jupyter notebook(s), uploaded to Toledo at least 24 h before the defense, then a defense in a timeslot you register for on Toledo. Every code block must be understood by both of us (we can be asked to explain or tweak it), so blocks are short and start with a one-line comment on what it does and what to tweak.

0.1 How the program runs

Robot::control() runs every 10 ms. In each call, in this order:

  1. Correction (if estimator on, robot.cpp:42-51): read front distance, CorrectionUpdate(...) → updates _xhat, _Phat, _nu; sends the a-posteriori estimate (ch 9) and the innovation (ch 10).

  3. Prediction (if estimator on, robot.cpp:95-98): PredictionUpdate(speedMotor, ...) with the measured wheel speeds → prior for the next 10 ms.
  4. Send channels 0–8 to QRoboticsCenter (robot.cpp:101-109).

0.4 State units: metres own reading of the new code

The new template reads the reference straight from QRC (xref(0) = readValue(0), no Meas2State) and computes desired_velocity = K * (_xhat - xref) (robot.cpp:59-61). That only works if the state is the distance itself:

$$x = d\quad[\text{m}],\qquad \text{desired wheel speed} = K\,(\hat d - d_{ref})\quad[\text{rad/s}]$$

Sign check: too far from the wall (\(\hat d > d_{ref}\)) ⇒ positive wheel speed ⇒ drives forward, towards the wall ✓. Too close ⇒ negative ⇒ backs off ✓. K > 0, in rad/s per m.

Changed vs. our first plan: the old template used \(x = -d/r\) in wheel radians (Meas2State = -1/R_WHEEL, still defined in robot.h:46 but now unused). With the new feedback sign that would drive the robot the wrong way. Use metres everywhere: x, xref, P, Q and R are all in m or m². Don't use Meas2State.

3.2 Which R?

  • An IR sensor like this has a 1/raw calibration (sharp41S.cpp), so the noise grows with distance. Expect a bigger variance at 0.28 m than at 0.10 m. own derivation
  • The linear filter has one fixed R. Take the value at the distance where the controller will work (the reference distance of Step 7), or the largest one to be safe. Mention the distance dependence in the report.
  • A constant bias (mean ≠ tape) isn't noise. R doesn't fix it; it shifts the whole estimate. Note it, and explain it as a sensor calibration error.

4.1 From speed noise to Q

The prediction subtracts \(r\Delta t\,\bar\omega\), with \(\bar\omega\) the mean of two noisy wheel speeds. If each wheel speed has standard deviation \(\sigma_\omega\) and the two wheels are independent:

$$\sigma_{\bar\omega} = \frac{\sigma_\omega}{\sqrt 2},\qquad Q = (r\,\Delta t\,\sigma_{\bar\omega})^2\ \ [\text{m}^2]$$

This is the A2 formula \(\mathbf Q = \mathbf B\mathbf G\mathbf B^\mathsf T\) with \(\mathbf B = [-r\Delta t/2,\ -r\Delta t/2]\) and \(\mathbf G = \mathrm{diag}(\sigma_\omega^2, \sigma_\omega^2)\). own derivation

Q from σω Python
# Q from the wheel-speed noise (A2 Step 6). Units: m^2, same as R.
# TWEAK: sigma_w = our measured wheel-speed std from A2 (rad/s).
dt, r = 0.01, 0.0325
sigma_w = 0.35                       # rad/s, example: one encoder count per sample (A2 Step 0)
sigma_m = sigma_w / np.sqrt(2)       # mean of two independent wheels
Q = (r * dt * sigma_m)**2            # m^2   -> goes into state_estimator.cpp
print(f'Q = {Q:.2e} m^2')

With the example σω = 0.35 rad/s: Q ≈ 6.5·10⁻⁹ m², inside the FAQ's typical range 10⁻⁹–10⁻⁵ m².

Q from speed noise alone ignores wheel slip and an imperfect wheel radius (A2: our r = 0.0312 vs. official 0.0325, a 4% scale error). If the filter lags in Step 5, that's the reason to increase it. Ch 4.9 calls a filter with too small Q "smug": it stops listening to the sensor.

5.1 The filter loop

1D Kalman filter, same order and units as robot.cpp Python
# 1D Kalman filter on a logged run: correction first, then prediction (as robot.cpp).
# State x = d [m], input = mean wheel speed [rad/s], measurement = front distance [m].
# TWEAK: Q, R (Steps 3-4), P0; columns (SET 3: speeds ValueIn2/3, distance ValueIn6).
df = pd.read_csv('data/F1_run1.csv', header=1, skipinitialspace=True)
w = (df['ValueIn2'] + df['ValueIn3']) / 2          # mean wheel speed, rad/s
z = df['ValueIn6']                                 # front distance, m

dt, r = 0.01, 0.0325
F, B, H = 1.0, -r*dt, 1.0
Q, R, P = 6.5e-9, 1.25e-5, 1e-4                    # m^2, m^2, m^2 (P0: sigma 1 cm)
x = z.iloc[0]                                      # start at the first measurement

xs, Ps, nus, Ss = [], [], [], []
for wk, zk in zip(w, z):
    nu = zk - H*x                                  # innovation (m)
    S = H*P*H + R                                  # innovation variance (m^2)
    K = P*H / S                                    # Kalman gain
    x = x + K*nu;  P = (1 - K*H)*P                 # corrected estimate (= robot channel 9)
    xs.append(x); Ps.append(P); nus.append(nu); Ss.append(S)
    x = F*x + B*wk;  P = F*P*F + Q                 # prediction for the next sample (= channel 8)

df['d_hat'] = np.array(xs)                         # a posteriori estimate, m
df['sd_hat'] = np.sqrt(Ps)                         # 1 sigma of the estimate, m
df['nu'], df['S'] = nus, Ss

6.1 state_estimator.cpp

state_estimator.cpp, filled in C++
#include "state_estimator.h"

// PREDICTION: x = d [m] shrinks by R_WHEEL * dt * mean wheel speed.
// TWEAK: Q (m^2) from Step 4/5.
void PredictionUpdate(const BLA::Matrix<2> &u, BLA::Matrix<1> &xhat, BLA::Matrix<1> &_Phat) {
  BLA::Matrix<1,1> F = {1.0};
  BLA::Matrix<1,1> B = {-R_WHEEL*TSAMPLE};        // m per (rad/s)
  BLA::Matrix<1,1> Q = {6.5e-9};                   // m^2  <- Step 4/5
  BLA::Matrix<1,1> v = {(u(0) + u(1)) / 2.0};     // mean wheel speed, rad/s

  xhat = F*xhat + B*v;
  _Phat = F*_Phat*~F + Q;
}

// CORRECTION: front distance z [m] = d.
// TWEAK: R (m^2) from Step 3/5.
void CorrectionUpdate(const BLA::Matrix<1> &y, BLA::Matrix<1> &xhat, BLA::Matrix<1> &nu, BLA::Matrix<1> &_Phat) {
  BLA::Matrix<1,1> R = {1.25e-5};                 // m^2  <- Step 3/5
  BLA::Matrix<1,1> H = {1.0};                     // state and measurement both in m

  nu = y - H*xhat;                                 // innovation, m
  BLA::Matrix<1,1> S = H*_Phat*~H + R;             // innovation variance
  BLA::Matrix<1,1> K = _Phat*~H*Inverse(S);        // Kalman gain

  xhat += K*nu;
  BLA::Matrix<1,1> I = {1.0f};
  _Phat = (I - K*H)*_Phat;
}

The structure is the template's; only the ?? are filled. TSAMPLE and R_WHEEL come from mecotron.h (already included).

7.1 The gain

desired_velocity = K * (_xhat - xref): error in m, output in rad/s (the velocity controller's reference), so K is in rad/s per m.

Units trap: FAQ tuning says "start with K = 0.5, typical 0.3–2.0". That was for the old radian state. In metres the same behaviour needs K ≈ 1/r ≈ 30 times larger: K = 0.5 would ask 0.5 rad/s for a 1 m error, the robot would barely move. own derivation

Rough feel (ignoring the fast velocity loop): the distance then follows \(\dot d = -rK(d - d_{ref})\), a first-order response with time constant \(\tau = 1/(rK)\). K = 30 → τ ≈ 1 s; K = 10 → τ ≈ 3 s. A 10 cm step with K = 30 asks 3 rad/s ≈ 0.1 m/s. own derivation

11.1 The model

State \(\mathbf x = [d,\ \omega_A,\ \omega_B]^\mathsf T\), input \(\mathbf u = [V_A, V_B]^\mathsf T\), A2 motor model \(\omega[k+1] = a\,\omega[k] + b\,V[k]\) per wheel:

$$\mathbf F = \begin{bmatrix}1 & -\tfrac{r\Delta t}{2} & -\tfrac{r\Delta t}{2}\\ 0 & a_A & 0\\ 0 & 0 & a_B\end{bmatrix},\quad \mathbf B = \begin{bmatrix}0 & 0\\ b_A & 0\\ 0 & b_B\end{bmatrix},\quad \mathbf z = \begin{bmatrix}d_{IR}\\ \omega_{A,enc}\\ \omega_{B,enc}\end{bmatrix},\ \mathbf H = \mathbf I_3$$ $$\mathbf Q = \mathrm{diag}(q_d,\ \sigma_{fit,A}^2,\ \sigma_{fit,B}^2),\qquad \mathbf R = \mathrm{diag}(\sigma_d^2,\ \sigma_\omega^2,\ \sigma_\omega^2)$$

Our A2 values: \(a \approx 0.66\), \(b \approx 0.69\) rad/s per V, one-step RMSE ≈ 0.43–0.48 rad/s → σfit. \(q_d\) small (only slip), e.g. the mandatory Q. own derivation from A2 Step 4

3-state filter with the motor model Python
# x = [d, wA, wB], u = [VA, VB], z = [IR, wA_enc, wB_enc]. Correct, then predict.
# TWEAK: aA, bA, aB, bB and fit RMSE from motor_model.csv; R; q_d.
mm = pd.read_csv('../ours_assignment_2/CSVE1E5/export/motor_model.csv').query('model == "linear"').set_index('wheel')
aA, bA, aB, bB = mm.a['A'], mm.b['A'], mm.a['B'], mm.b['B']
F = np.array([[1, -r*dt/2, -r*dt/2], [0, aA, 0], [0, 0, aB]])
B = np.array([[0, 0], [bA, 0], [0, bB]]);  H = np.eye(3)
Q = np.diag([6.5e-9, mm.rmse_fit['A']**2, mm.rmse_fit['B']**2])
R = np.diag([1.25e-5, 0.35**2, 0.35**2])
u  = df[['ValueIn0', 'ValueIn1']].values                       # applied voltages (SET 3)
zs = df[['ValueIn6', 'ValueIn2', 'ValueIn3']].values           # IR, wA, wB
x = zs[0].copy();  P = np.diag([1e-4, 1.0, 1.0])
for k in range(len(df)):
    S = H @ P @ H.T + R;  K = P @ H.T @ np.linalg.inv(S)
    x = x + K @ (zs[k] - H @ x);  P = (np.eye(3) - K @ H) @ P
    x = F @ x + B @ u[k];  P = F @ P @ F.T + Q

11.2 Watch out

  • Low voltages: near the reference the controller sends small voltages, where friction matters most and our linear fit (3–9 V) is least accurate. Compare the predicted and measured wheel speed at 0–2 V (an F2 slow start, or the F3 logs). If off: raise σfit or use the Coulomb variant from A2 (USE_COULOMB, adds a constant per sign of ω).
  • Which voltage: use the voltage that was applied. The template clamps uA to ±20 V, but the motor driver can't give more than the battery; in the F3 logs ch 0/1 is the command, not necessarily what the motor got.
  • Wheels in the air / pushed by hand: the model says ω follows V; when the robot is pushed with V = 0 the encoders must win. That's the R vs. σfit balance, a nice live demo.
